THE REUSABLE ENGINEERING PATTERN

Every vision app is a chain of choices.

  1. Capturecamera, image, video, resolution, conditions
  2. Preparecrop, resize, normalise, enhance, reject bad input
  3. Interpretrules, contours, landmarks, classifier, or detector
  4. Decideconfidence, thresholds, task-specific logic
  5. Evaluateaccuracy, speed, failure, fairness, privacy

METHOD SELECTION

Use the simplest method that survives reality.

Rule-based vision Strong when colour, shape, camera position, and lighting are controlled. Fast and explainable.

Learned vision Strong when objects vary across real scenes. Requires confidence, representative data, and testing.

AFTER THE RUN

Turn an output into
evidence.

Do not say “it worked.” State what the system received, what it changed, what it returned, and when the result should not be trusted.

InputWhich image, camera frame, resolution, and lighting?

TransformationWhich colour conversion, crop, threshold, or model?

OutputWhat was detected, measured, labelled, or missed?

EvidenceWhich changed condition would prove the result is robust?

TEST FAILURE BEFORE TRUST

One object can produce five different results.

A demo that works once is not a reliable system. Deliberately test the conditions that should make it struggle.

Lightingshadow, glare, colour shift

Motionblur and missed frames

Visibilityocclusion, crop, distance

Contextangle, background, clutter

CONFIDENCE IS NOT TRUTH

A score tells you how certain the model feels.

False positiveThe system finds something that is not there.

False negativeThe system misses something that is there.

ThresholdHigher confidence reduces weak predictions but can hide valid ones.

PEOPLE ARE NOT TEST DATA

Useful vision must be responsible vision.

ConsentPeople should know when and why a camera records them.

PrivacyCollect less, keep less, and avoid identity claims when detection is enough.

BiasTest across people, environments, lighting, and contexts.

Human judgementKeep a person accountable for consequential decisions.

DESIGN, THEN CODE

Frame one problem worth solving.

Start with a real decision, a clear user, a visible input, and a testable success condition.

ExampleCount occupied study-room seats.

InputFixed camera; no identity recognition.

OutputCount, confidence, and an uncertain state.

TestLighting, blocked seats, bags, movement.
